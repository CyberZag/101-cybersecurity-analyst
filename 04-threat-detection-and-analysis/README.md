# 04 Threat Detection and Analysis

A portfolio-ready study module based on the Threat Detection & Analysis section of *The Complete Hands-On Cybersecurity Analyst Course*. It covers the SOC analyst's core loop: triaging security events, using EDR tooling, and writing/tuning detection rules.

## Learning objectives

By the end of this module, I can:

- Describe the SOC alert lifecycle: generation → triage → escalation/closure.
- Explain what an EDR agent monitors (process creation, network connections, file/registry changes) and how that data supports investigation.
- Write a basic detection rule (e.g., a Sigma rule or SIEM search) for a specific behavior.
- Distinguish a true positive from a false positive and document the reasoning.
- Explain why false-positive tuning matters for analyst workload and alert fatigue.

## Concept map

| Topic | What it does | Analyst relevance |
|---|---|---|
| Alert triage | First-pass review of a generated alert | Decide escalate / close / needs more data, fast |
| EDR telemetry | Process, network, file, registry events from endpoints | Primary evidence source for most host-based investigations |
| Detection rules | Logic (e.g., Sigma, SPL, KQL) that turns raw telemetry into an alert | The core artifact of detection engineering work |
| False-positive tuning | Refining a rule/alert to reduce noise without losing true positives | Directly affects analyst workload and alert fatigue |
| Severity/priority | Business/asset-context-aware ranking of an alert | Determines response order in a busy SOC queue |

## Key notes

### The SOC alert lifecycle
An alert is generated by a detection rule or EDR heuristic, then triaged by an analyst who gathers context (host, user, process tree, network connections) before deciding to escalate, close as benign, or request more data. Documenting the reasoning at each step is what makes triage auditable.

### EDR as an evidence source
EDR agents typically log process creation (with command line and parent process), network connections, and file/registry modifications. Reading a process tree (parent → child relationships) is often the fastest way to spot living-off-the-land or script-based abuse.

### Writing detection logic
A detection rule expresses "if this pattern of telemetry occurs, alert." Sigma is a common vendor-agnostic rule format; SIEM-native query languages (SPL for Splunk, KQL for Sentinel/Elastic) do the same job within a specific platform.

### False positives and tuning
Every new detection rule needs a tuning pass — checking it against known-benign activity and adjusting thresholds/exclusions so it doesn't drown the queue in noise, without becoming so narrow it misses the real behavior.
